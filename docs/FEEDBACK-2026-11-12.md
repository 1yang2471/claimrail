## 反馈 1（已修）：CLI 入口把仓库解析短路了

`hook()` 的解析链是 payload.cwd → `ZCODE_PROJECT_DIR` → 进程 cwd，但 CLI 入口把 `flags.cwd`（=钩子进程自己的 `process.cwd()`）传了下去——payload/env 两条路成了死代码。实测复现：在 forklight 里手动跑 `hook`、payload 指向永雏小菲，钩子去查了 **forklight 的台账并静默放行**。真实宿主每次都带 env 兜底才没翻车；换任何一个不带 env 的宿主，门就挂错仓库。
修法：入口对 hook 不传 `cwd`，解析链按设计生效。测试钉住三级顺序（payload > env > 进程 cwd），变异：还原短路 → 红。顺带发现：**ZCode 会话里跑测试会泄漏本会话的 `ZCODE_PROJECT_DIR` 给子进程**，测试已剥该变量。

## 反馈 2（已修）：拦截文本会被宿主腰斩到 4000 字符

宿主源码 `KRa→kce`：Stop 拦截原因截到 **4000 字符**。永雏小菲真实台账（40 条分叉、37 条需你定）的全量拦截文本 **22.5KB**——直接交出去模型只能见到前一半，SKILL.md 要求的"一次问完"做不到。修法：`compactStopBlock` 用 check 的结构化数据重排（一行摘要 + 尽可能多的单行条目 + 必保的收尾指令），实测压到 **2698 字符**、37 条全量可见。变异：拆压缩 → 红。

## 反馈 3（记为边界）：钩子崩溃 = 宿主 fail-open

那 4 次崩溃的原因未在当前版本复现（0.2.5 时代，最可能是 claimrail 自己开发中途源码被打断——四个失败时刻与本项目两个深夜开发窗口重合）。但宿主语义已经从源码裁定：钩子进程异常 → `hook.run.failed` → **不拦，交付照常放行**。也就是说门会以"静默消失"的方式失效，而不是 fail-closed。这是宿主语义，claimrail 侧改不了；记入边界，别把"没有拦截记录"读成"没有违规"。

## 反馈 4（记为边界 + 待用户决策）：项目根不是仓库的会话门看不见

会话的工作目录是 `D:\workspace`（工作区根，非 git 仓库）时，钩子静默放行——门对这类会话全盲。永雏小菲 11-11 之后的会话很可能正属于此。这不是 claimrail 能修的（不能替用户 git init），但用户可以：把工作区根变成仓库，或接受这类会话不受门管。

## 反馈 5（待用户决策）：钩子没带 --allow-net，precedent 档在真实会话里必然回验失败

钩子命令没有 `--allow-net`，所以真实会话里 precedent/web 证据一律"未获同意，不得外发查询"→ 永雏小菲这类设计文档仓库**每次交付都会被 37 条问题拦住**。这是设计行为（"问人，不是照默认来"），但有两个代价：外发查询要你同意才开；不开的话设计类仓库的每次交付都要人工答一轮。选项见交差报告。
