## 四项活体探针

临时 git 仓库（不在项目内），每项都跑真实的 `node src/cli.mjs check`：

1. **`verified` 字段对判定零作用**：同一台账只把 `verified` 从 `true` 改成 `false`，两次
   `check --json` 输出逐字节相同，都 exit 0。它不是安全洞（证据照样被回验），但会让模型
   误以为写 `verified: true` 有用。
2. **申报无分叉可静默通过**：本次改动新增 `src/page.tsx`（UI 文件），台账写 `forks: []`
   加一句 `no_fork_reason`，`check` exit 0，输出「申报无分叉」——程序没看 diff。
3. **同一改动申报一条分叉**：`evidence: null`、`cost_if_wrong: low`，同样 exit 0，但末尾
   点名「未验证 1 条」。差别只在可见性，不在拦截。
4. **已推送的普通提交**：push `origin/master` 后再跑 `check`，判 `high` 并 block，理由写
   「已发布或有副作用：pushed:HEAD」。代价判 high 是保守设计，可以接受；问题是措辞把
   "已推送"说成"已发布"，会让人去查错方向。

## 随后落地：published 收窄（同日）

用户选了"两者都做"。第一版按"当前分支上游是不是默认分支"写，探针立刻抓到一个假低：
`git push origin HEAD:main` 不设置上游，旧写法会把"已经在默认分支上"判成未发布。
改成直接问 git"哪些远端分支包含 HEAD"（`branch -r --contains HEAD`）——这一步同时覆盖
功能分支、已合并、本地领先三种形状，也不漏不设上游的推法。默认分支优先读 `<remote>/HEAD`，
读不到只认该远端下唯一一个 main/master，两个都在或都没有 → `null` → high。
理由句改成「已推送/已发布或有副作用」，并带上游名（`pushed:origin/main`）。

测试 325 → 335；六条变异（去掉默认分支成员判断 → 红 1、未知退回 false → 红 2、
去掉 main/master 兜底 → 红 3、去掉 `--contains` → 红 2、理由句退回 → 红 1、
去掉上游名标签 → 红 1）全部红→绿。
