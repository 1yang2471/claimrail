# PRD：forklight —— 让 AI 的选择留下痕迹

状态：待批准。名字暂定，改名只需一次 `git mv` + README 一处。
本文件是 14 轮逐项盘问的结论汇总，不是草案。凡本文未写的范围，v1 不做。

---

## Problem Statement

规格没写完的时候，AI 必须输出点什么，于是它输出它见过最多的那个做法。

用户看到的东西不是"随机选择的结果"，而是一个看起来已经想清楚的成品。岔路口被走掉了，且没有任何地方记录"这里曾经有岔路口"。所以用户无法在错误还便宜的时候介入——只能在实物做完之后，用一句"感觉不对"来描述一个已经不可逆的决定。

具体的痛感长这样：前端代码每一行都合法，`overflow-y: auto` 写得没错，但滚动条压在右对齐的聊天气泡上，用户自己的消息被遮住了。AI 检查过自己的代码，代码是对的，于是交差。它从来没看过渲染结果，也没告诉你它在一个你根本不知道存在的选项之间替你做了主。

更深一层的问题不是品味差。用户其实说不出自己想要什么——但人能在实物面前立刻说"不是这个"。现有的解决思路（不管是提示词还是提问）都要求人先描述偏好，这恰好是人做不到的那件事。

## Solution

把每一步需要品味或需要自信的判断，替换成一个外部可计算的量。

AI 在行动前必须写一份**决策台账**：这个任务里有几个规格没定的分叉、每个分叉的候选是什么、选了哪个、凭什么。台账由一个程序校验——结构齐不齐、声称的证据能不能回访、改动代价由程序自己从仓库状态算出来。校验不过，交付不出去。

三根支柱：

1. **台账 + 结构校验**：分叉必须申报。没被申报的分叉是这套机制唯一看不见的洞，用可统计的方式审计，不靠模型自觉。
2. **程序算代价**：`cost_if_wrong` 不由模型填。程序读 fan-in、是否已发布、有无外部副作用，自己算出 low/high；模型只能上调，不能下调。取不到值一律 high。
3. **偏好闭环**：用户否决过的东西只追加进原始 log；同一条否决命中两次以上才升格成规则，且每条规则带出处指针，能当场作废。这套机制记住的不是"人类一般喜欢什么"，而是"这个人在这个仓库里拒绝过什么"。

约束力不来自提示词写得强硬，来自有一个东西在它交付前把门关上。

### 与现有产品的差异

[antfu 的 web-design-guidelines](https://github.com/antfu/skills)（star 数 [TK: 复核，第三方页显示约 4.8k]）包装 Vercel 的 `web-interface-guidelines`（100+ 条，数量 [TK: 复核]），做的是**读代码、按公开规则匹配、输出 `file:line`**。这条赛道已经有人占住，且做得比我们好。

forklight 不重写那份清单，把它当上游引用。我们的差异在两处它结构上不可能做的事：

- **它读代码，我们看实物。** 渲染截图、几何相交、时间戳新旧——代码层面合规的缺陷在它那里查不出来。
- **它对齐公开共识，我们对齐具体的那个人。** 公开清单给的是平均值；`memory/log.md` 给的是你的否决记录。

发布文案必须能一句话把这两条说出来，且必须有基准数字撑着（见 Testing Decisions）。

## User Stories

### 使用 AI 的人

1. 作为用户，我想在 AI 动手前就看到"这里有两个做法，我选不了，你选"，这样我不用等实物做完才发现方向错了。
2. 作为用户，我想看到一屏以内的分叉清单，按"改回来有多贵"排序，这样我先处理最贵的那个。
3. 作为用户，我想每条分叉只看到三行（是什么、选了啥、凭什么），这样它不会被当成文档跳过不读。
4. 作为用户，我想清单里的位置是可直接点开的 `file:line`，这样我不用自己去找。
5. 作为用户，我想在实物交付后能一眼看到"哪几条 AI 没能验证"，这样我知道哪里还欠一次人工检查。
6. 作为用户，我想对 AI 的产出说一句"不要这样"之后，下次它真的不再这样，这样我不必重复同一个反对意见。
7. 作为用户，我想废掉一条它自己总结出来的偏好规则，且能立刻看到它是从哪几次否决归纳来的，这样它不会把偏见固化。
8. 作为用户，我不想改一个错别字也被要求填台账，这样工具不会第一天就被我关掉。
9. 作为用户，我想任务被打断的次数有上限（目标：中位数 ≤1 次/任务），这样这套东西是可用的而不是新的负担。
10. 作为用户，我想 AI 明确告诉我"这条我没能视觉验证，原因是 X"，而不是静默跳过，这样跳过是有痕迹的。

### 正在执行的 AI agent

11. 作为 agent，我想有一份 schema 固定的台账可写，这样"要不要申报分叉"不是我的主观判断，而是字段齐全与否。
12. 作为 agent，我想代价档位由程序算好给我，这样我不必给自己的错误估价，也不必说服自己"这次改回来很容易"。
13. 作为 agent，我想在证据取不到、人也不在的时候有一条确定规则可循（低代价选最容易改回来的做法并标记），这样我不会卡死，也不会假装知道。
14. 作为 agent，我想台账里引用仓库既有做法时必须写 `file:line` 且程序会去重读确认，这样我不会用一句"参考了现有代码"糊过去。
15. 作为 agent，我想有一个明确的"够用了就停"的证据取用顺序，这样我不必为了一个分叉去联网搜三圈。

### code review 的人

16. 作为 reviewer，我想在 PR 里直接看到台账 diff，这样我 review 的是决定而不只是代码。
17. 作为 reviewer，我想台账里禁止内联代码片段，这样它进 git 不会把实现细节外泄。
18. 作为 reviewer，我想看到一个声明了"本任务无分叉"的字段和它的类别，这样长期来看哪个类别从来不长分叉就是我要去抽查的地方。

### CI / 无人值守

19. 作为 CI，我想 `npx forklight check` 用退出码说话，这样约束力不依赖任何人的记性。
20. 作为夜间任务的使用者，我想高代价且无证据的任务直接停下来等确认，这样过夜跑出来的不是一个建错的成品而是一句"我卡在这儿"。
21. 作为项目维护者，我想偏好 log 和截图默认不进 git，这样个人品味数据和真实产品画面不会跟着仓库外流。

### web 前端领域

22. 作为用户，我想 AI 改完前端被强制跑一遍几何检查，这样"滚动条带与文本节点相交"这类缺陷在交付前就被拦下。
23. 作为用户，我想截图必须比最后一次代码改动新，这样 AI 不能拿上周的图证明今天没问题。
24. 作为用户，我想页面起不来时工具明确报"无法到达该路由"，而不是假装检查通过。
25. 作为需要登录的项目的用户，我想复用一份 Playwright `storageState`，这样我自己举的那个聊天页例子能被真的覆盖到。

### 文档 / API 设计领域

26. 作为文档使用者，我想文档类改动的代价由"有多少页面链接到它"决定，这样被广泛引用的规范文档不会被随手改写。
27. 作为 API 使用者，我想接口类分叉的代价由导出符号的引用数和是否已发版决定，这样破坏兼容性的改动会在动手前问我。
28. 作为用户，我想这两个领域用的是同一个代价函数，而不是各自的一套感觉，这样我不必怀疑哪套档位是编的。

### 安装与维护

29. 作为新用户，我想安装时看到一次数据去向说明（台账进 git、log 不进 git），这样不用事后猜。
30. 作为跨 agent 用户，我想 `SKILL.md` 层在任何支持该格式的工具里都能装，约束层（CLI）单独按需装，这样我至少能用上仪式部分。
31. 作为升级者，我想台账 schema 带版本号，这样旧文件不会被新校验器静默判过。

## Implementation Decisions

### 模块划分

八个模块，核心深、外壳浅。深模块全部可脱离 agent 独立测试。

| 模块 | 对外接口 | 深度所在 |
| --- | --- | --- |
| `ledger` | `record(forks)` / `read()` | schema 校验 + 版本 + 原子写；"禁止内联代码块"在这里 |
| `cost` | `grade(Observation) → low \| high` | 纯函数，无 I/O；三输入 + null→high |
| `evidence` | `verify(claim) → {ok, why}` | 按 kind 分派四档回验；时间戳新鲜度在这里 |
| `observe` | `observe(ctx) → Observation` | 唯一碰 git/依赖图/AST/渲染的地方；适配器落在这层 |
| `gate` | `decide(ledger, grades, evidences) → block \| proceed \| halt` + 一屏渲染 | 呈现规则与阻塞规则都在这里 |
| `memory` | `recordRejection(e)` / `rules()` / `invalidate(id)` | 两次升格 + 出处指针 + 可作废 |
| `hooks` | 宿主接线（Claude Code / Cursor / ZCode / CI） | 刻意做薄，不放逻辑 |
| `bench` | `run(tasks, {protocol:'on'\|'off'}) → metrics` | 陷阱任务库 + 红队探针 |

关键设计取舍：`cost` 的核心不接受"领域"参数，它只接受一个归一化的 `Observation`。三个适配器各自负责在自己的领域里把三个值读出来。这样"文档和 API 的代价靠感觉"这个风险从结构上被排除——感觉进不了 `Observation`，只有可数的东西能进来。

### 台账结构（决策形状，非最终字段名）

```jsonc
{
  "schema": 1,
  "task_class": "ui-new | docs-new | api-design | refactor | bugfix-known-cause | typo | rename",
  "forks": [
    {
      "fork": "一句话：规格没定的是什么",
      "options": ["候选A", "候选B"],
      "picked": "候选B",
      "evidence": { "kind": "repo|memory|render|web", "ref": "Chat.tsx:88 | log#3 | chat@1280.png | https://…" },
      "cost_if_wrong": "high",       // 程序覆写，模型只能上调
      "verified": true,              // evidence 为 null 时必须为 false
      "options_cost": { "候选A": "low", "候选B": "high" }  // observe 供给，可缺省
    }
  ]
}
```

`forks: []` 允许，但必须带 `task_class`，且每次空申报全部落盘可统计。空申报不设自动升级规则（v2 再根据数据决定）。

### 代价计算

三个输入，任一取不到 → `high`：

- **fan-in**：引用计数（依赖图 / LSP / 文本引用兜底）
- **published**：是否已进入收不回来的产物——打过 tag、发过包、提交并推送、线上 URL 可访问、被他人链接过
- **irreversible**：有无外部副作用——删除、数据迁移、发消息、写第三方、部署

两档制，不设 medium。门本身是二值的，第三档只会变成讨价还价的地方。

`danger` 侧的现成接入点：工作区已有的破坏性操作守则（递归删除前 dry-run、路径展示、盘符根/系统目录硬拦截、`safe-remove.ps1`）作为 `irreversible` 的实现，不新写一套。

### 证据四档

顺序严格，够了就停：`repo → memory → render → web`。

- `repo`：重读引用的 `file:line`，确认存在且确含声称的模式。
- `memory`：确认 `log#n` / `rules#n` 存在。
- `render`：截图存在且 mtime 晚于最后一次相关代码改动，**并且同目录的度量报告里被断言的检查项必须严格为绿**。只有截图没有报告 = 看了图没判过，不成立；报告里全是不作数（null）= 采集器空转，也不成立。
- `web`：回访 URL 返回 200 且内容含声称要点；默认需用户同意后才发请求（涉及项目名/内部信息）。

`web` 排最后是因为它最慢、最不稳，且是唯一能编出"好评率"这种不存在度量的一档——在仓库里连被编造的机会都没有。

### 渲染检查的三态判定（实现期确定）

每项检查返回 `true`（判过且绿）、`false`（判过且红）、`null`（没数据，不作数）。第三态是被逼出来的：采集器某一类元素没采到时，两态设计只能选红或绿，而选绿就等于把"我没看见"说成"没问题"——那正是这套产品要根除的原始毛病。证据回验只认 `true`。

同一形状还出现了第二次：焦点环探针无法在纯 JS 里产生真实键盘焦点，`hasVisibleFocus` 一律返回 `null`，于是该项判 `null` 而不是绿。降级状态必须在判定层保留，否则采集器的诚实会被下游抹掉。

v1 的五个检查及其阈值（全部为可判定的硬事实，不含品味）：

| id | 判红条件 | 阈值 |
| --- | --- | --- |
| `scrollbar-clears-text` | 纵向可滚且未预留布局宽度的容器，其右侧滚动条带与任何文本矩形相交 | 覆盖条带宽 15px |
| `bottom-not-covered` | 滚动容器最后一个内容项与固定/粘性元素矩形相交 | — |
| `touch-targets-ok` | 可交互元素包围盒短边不足下限 | 44px |
| `contrast-ok` | 正文对比度低于 WCAG 门槛（大字号走低档） | 4.5:1 / 3:1，24px 或 18.66px 加粗算大字 |
| `focus-visible-ok` | 聚焦时 outline/shadow/border 无可测变化 | v1 一律 `null`，待驱动层真实键盘事件 |

经典滚动条（`offsetWidth - clientWidth > 0`）挤走布局宽度，不判红——只有覆盖式才会压内容，这与原始例子的成因一致。

条带的存在还要再排除两种"根本没画条"的情况，都是实测补上的：`scrollbar-width: none`（不画）、`scrollbar-gutter: stable`（已预留）。缺了这两个豁免就会假红。反过来，实测本机 headless Chromium 对默认 `overflow-y: auto` 的容器给出 `reservedX = 0` 且 `scrollbar-width: auto`——也就是**这个运行时用的是覆盖式滚动条**，默认写法不加右内边距确实会压住右对齐内容。所以"修好"的形态是 `scrollbar-gutter: stable` + 右内边距，而不是"保留默认滚动条就行"。

`bottom-not-covered` 同样被实测纠正过一次：原先拿"最后一个内容项"和固定条比，列表一溢出末项就在屏幕外，永远不相交——最典型的遮挡反而漏判。改为结构性比较：滚动容器自身矩形是否与固定条重叠。并且固定条要带 `inside`（它归属的滚动容器），否则容器自己的 sticky 子元素（日期分隔条那种）必然重叠，会造出一类很常见的假红。

多视口不是可选配置：坏页在 1280 宽下文字不折行、列表不溢出，`scrollbar-clears-text` 合法地为绿；同一份缺陷在 390×700 才暴露。只跑宽屏等于把这类缺陷整体放过。

判定层不含任何浏览器调用：`page` 只需要 `evaluate()` 与 `screenshot()` 两个方法，因此这一层可以用手写的假页面测透，驱动选型不阻塞测试。

### 阻塞与降级

- 高代价 + 无证据 + 人在场 → 开工前阻塞，等一句话。
- 高代价 + 无证据 + 人不在场 → 硬停（退出码 1，任务不产出成品）。
- 低代价 + 无证据 → 在候选中选 `cost_if_wrong` 最小的做法，标 `unverified`，交付开头汇总。
- 有证据 → 不打断，只存档。

页面不可达时的降级分支必须留下可见文字（"未视觉验证：dev server 未在 5173 响应"），禁止静默通过。v1 只实现"给一个 URL"入口 + `storageState` 登录态复用；seed 数据、Storybook 单组件模式、静态 preview 推 v2。

### 实现期确定的扫描对象规则（`observe`）

副作用扫描只作用于**新增行**，且排除 `test(s)/`、`fixtures/`、`docs/`、`*.test.*` 以及规则表自身所在文件。原因不是洁癖：规则表文本里必然含 `rm -rf`、`DROP TABLE`、`npm publish` 这些形状，扫全文等于任何一次改动都判定"有不可逆副作用"，门在第一天就彻底失灵。测试数据与文档里的命令不是动作。

CLI 的实际表面：`forklight init`（建 `.forklight/decisions.json`、补 `.gitignore` 三条、打印一次数据去向）和 `forklight check [ledger] [--cwd] [--ledger] [--unattended] [--allow-net]`。退出码 0 放行 / 1 拦住；结构不合规时不进入后续检查——先修申报，再谈代价。`check` 会把程序覆写的档位打出来（`申报 low → 程序 high（原因）`），这一步不留痕迹就等于没拦。

### 第四条门规则（盘问之外补入，已确认保留）

写 `gate` 时补了第四条拦截规则，因为它是原始诊断最直接的形状：**无证据 + 候选代价数据齐全 + 却选了改起来更贵的那个候选 → 拦**。没有依据时滑向熟悉做法，而熟悉做法往往恰好更贵（改一个 token vs 重做信息架构）。

它不引入新的判断来源，仍用同一个 `cost` 函数和同一份 `Observation`；候选档位数据不齐时**放弃判定**——误拦一次的代价比漏拦一次高，因为一次误拦就教会用户无视整屏清单。有证据时选贵做法属于知情决定，不拦。

### 记忆结构

`memory/log.md` 只追加，是唯一真相。`rules.md` 是可删除可重建的缓存，同一条否决命中 ≥2 次才升格，每条带 `[来源: log#n]`。正向参照物（`anchors`）单独记。读取时 rules 全读，log 只读最近 20 条。

### 上游依赖

Vercel 的公开清单作为 `references` 的上游来源引用（每次拉取或固定版本快照），不复制进我们的规则库、不自行维护第二份 100 条。

## Testing Decisions

好测试的标准：只断言外部行为，不断言实现细节。`cost.grade()` 给一组 `Observation` 进、一个档位出；`evidence.verify()` 给一条 claim 进、`{ok, why}` 出；`gate.decide()` 给台账进、一个三值决定出。这三个都不碰文件系统之外的东西，时间通过参数注入，因此"截图必须比代码新"这类规则可以用假时钟测。

三层，缺一不可：

1. **单元测试**（必做，覆盖 `cost` / `evidence` / `ledger` / `gate` / `memory`）
   - 三输入任一为 null → high；只上调不下覆的行为；两档不存在第三值。
   - 假 `file:line` 引用、假 `log#n`、旧截图、404 URL 分别必须让 `verify` 返回 false。
   - 台账里内联代码块超过一行 → schema 校验失败。
   - 同一条否决命中一次不升格、命中两次升格、带指针的规则被 `invalidate` 后不再出现在 `rules()`。
2. **埋雷对照基准**（核心主张的唯一证据）
   - 20-30 个任务，每个埋一个已知的众数陷阱：仓库里明明有惯例但外部最常见做法不同；或存在高代价分叉而默认走法恰好不可逆。
   - 同一批任务跑两遍：有协议 / 无协议。
   - 报四个数：静默塌缩率、高代价分叉在动手前被拦住的比例、每任务打断次数中位数、额外耗时中位数。
   - v1 上限目标：打断中位数 ≤1 次/任务，额外耗时中位数 ≤90 秒。**成本指标和拦截指标同权重**——只测拦截量，最优解就是把所有任务都拦下来，那东西会拿满分然后被所有人关掉。
3. **红队**（必做）
   - 断网、给不存在的路径、清空 `log.md`，看它是老实硬停，还是当场编造一条 `log#7` 或一个 URL。
   - 判定标准：任何一条"声称但程序回验不了"的证据都必须导致失败，不是警告。

发布文案里那句对比数字必须来自第 2 层的真实运行结果。没跑出来就照实写"尚未测量"。

prior art：`bench/tasks/*` 的结构参照"带 fixture 的静态分析工具测试集"（每个任务目录含输入仓库快照 + 一个 `trap.md` 描述陷阱与期望行为），不是单元测试文件。

## Out of Scope

v1 明确不做：

- 第二模型/异体评审当门。两个模型常共享同一个众数，第二个模型同样觉得紫渐变很安全——同病的人互相签字不叫约束。
- 问题攒批队列作为阻塞的替代。队列期间默认值已经建下去了，管不住唯一需要管的那类。攒批本身可作为附加层，v2 再评估。
- 开工前一次性摊开所有分叉让人签字。人能在实物面前拒绝，在没看见的东西面前排序是猜的。
- 所有任务都建台账；模型自评复杂度决定是否启用协议；模型自评 `cost_if_wrong`（只允许上调）。
- 三档及以上代价档位。
- 第四个领域（命名、图表、视觉设计之外的东西）。
- 全覆盖可达配方：seed 数据、Storybook 单组件模式、静态导出 preview。
- 纯提示词包发布形态；VS Code 扩展（约束对象错了——要治的是自主行动的一方，不是编辑器里的人）。
- 空申报的自动升级规则（先拿数据）。
- 任何"调研高分产品并自动对齐"的管线。

## Further Notes

几个需要复核的事实与开放风险：

- 上游清单的具体规则数量、star 数均来自第三方页面，发布文案引用前需回原仓库核实（见上文两处 `[TK]`）。
- **最大风险不是漏检，是疲劳。** 这套机制的失败模式不是它查不出东西，而是用户第 20 次看到台账后开始无条件放行。基准里的打断中位数是为此设的哨兵，如果实测压不到 ≤1，宁可减少纳入的代价维度，也不要保留一个让人学会闭眼的工具。
- **`published` 输入的判定在 monorepo / 无 tag 仓库里可能普遍取不到值**，按规则会大量升 high，导致阻塞过频。这是最可能在真实项目里翻车的一处，基准要专门放一两个这种仓库进去测。
- 4.8k star 的邻居已经把"审计前端 UI 代码"这句话占了。我们的发布文案如果写得像"又一个 UI 检查工具"，会被直接归到它下面。定位必须落在"留下痕迹 + 记住你拒绝过什么"，而不是"检查得更全"。
- **真站 dogfood 首轮（2026-11-06，FreeCast 扩展 UI + Shinsekai docs 静态页）**。四类假红全部来自"样式采样能代表视觉效果"这个假设，四条都已在实现里改掉：
  1. 走不到实色背景就兜底白色 → 白字药丸标签被判 1.00 对比度，单页 83 处假红。改为返回 `null`（未判）。
  2. 半透明层不合成 → `rgba(0,0,0,.05)` 被当纯黑，103 处文本里 76 处报红、最低 1.53。改为逐层合成；最底层仍半透明则未判。
  3. 正文里的行内链接按控件标准考核 → 16 处假红。`inline` 元素不参与触摸目标检查。
  4. `nameFromUrl` 只取 URL 末段 → 三个不同页面的报告同名互相覆盖，**真丢过一次证据**（审查时列为 P2，实测代价是证据被偷换）。现在名字带 URL 指纹。
- 两个**前提级**发现，比假红更重要：
  - Shinsekai 不是 git 仓库 → `fanIn`/`published`/`irreversible` 三者全取不到 → 每条分叉都判 high。forklight 在非 git 项目上接近全盲，发布时必须写明这条边界，或者提供一个显式的"非 git 模式"降级。
  - Vite SPA 用 `file://` 打开是空白页：五项全部"未判"，且报告无法被引用（0 项绿）——"采不到就不作数"在这里表现正确，但也说明**没有 dev server 或 storageState 就测不到真实前端**。dogfood 的下一轮必须起服务。
- `contrast-ok` 在磨砂卡片 + 渐变背景的设计上覆盖率只有 7/111，几乎不判。样式层面拿不到真实底色，**要靠像素采样（读截图中文字背后的实际像素）**才能判。列为 v2；在那之前这一项对现代设计语言的检出率要如实写低。
- FreeCast 仓库有 5 个 tag 且 `origin/main` 有上游 → `published` 非空 → 任何改动都判 high。设计意图（已发布产物收不回来）在真仓库上确认成立，不是只在 fixture 上成立。
- 名字待定。`forklight` 取"让岔路口可见"，与台账机制一致。
- **驱动层未决（阻塞 `forklight web` 真正跑起来）**：判定层与采集器已完成并有测试，但本机没有 Playwright 也没有浏览器缓存，所以截图和真实焦点事件都还没有出口。两条路各有代价：装 Playwright（依赖重、要多下载一个浏览器，但 `storageState` 与真实键盘事件都是现成的）；或用系统 Edge 走裸 CDP（零新依赖，Node 自带 WebSocket 就能连，但启动参数、端口发现、消息解析都要自己维护）。焦点环那一项在两条路上都要靠真实键盘事件才能从 `null` 变成可判。
